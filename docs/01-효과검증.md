# 1. 효과 검증: 기존 방식과 에이전트 방식 비교

## 1.1 목적

"빨라진다"는 느낌이 아니라 **같은 과제를 두 방식으로 만들어 소요 시간과 결함 수를 비교**한 숫자로 판단한다.

## 1.2 실업무 적용 사례: AI 교과목 이수율 조회 화면

통제된 실험 전에, 실제 업무에 적용한 결과를 먼저 기록한다. 연습용 과제가 아니라 **공문으로 접수된 개발 요청**을 7회차 에이전트로 처리해 반영한 건이다.

| 항목 | 내용 |
|------|------|
| 요청 | AI 교과목 이수율 조회 화면 개발 (공문 접수) |
| 화면 유형 | 조회형 (이수율 집계 포함) |
| 예상 공수 | 약 1주 (기존 방식 기준 추정, 5일 × 8시간 = 약 40시간) |
| 실제 공수 | 반나절 (약 4시간) |
| 단축 | 약 90% (예상치 대비) |
| 범위 | DB 설계, SP 작성, 화면 코드 |
| 결과 | 실업무에 반영 |

**어떻게 했는가**

1. **나만의 코딩 베이스를 스킬로 만들어 활용**: 평소 쓰던 정규식 처리, 공통 패턴 등 다양한 방식의 코드를 정리해 에이전트 스킬로 묶었다. 에이전트가 일반적인 코드가 아니라 **내 방식대로** 코드를 만들게 되어, 생성물을 고치는 시간이 줄었다.
2. **이해가 안 되는 부분을 스킬로 풀어서 설명받음**: DB 설계와 SP 작성 후, 생성된 코드 중 이해가 안 되는 부분은 설명용 스킬로 쉽게 풀어 달라고 했다. 모르는 코드를 그대로 반영하지 않고, 이해한 뒤 반영했다.

**해석할 때 주의할 점**

- 기준값(1주)은 실측이 아니라 **예상치**다. 그래서 1.3의 비교 실험으로 기존 방식의 실제 공수를 따로 재야 한다.
- 사례가 1건이고 조회형 화면이다. 등록·수정형이나 결재 연동 화면에서도 같은 효과가 나는지는 따로 확인해야 한다.
- 작성자가 스킬을 직접 만든 사람이라 효과가 가장 크게 나오는 조건이다. 스킬을 쓰기만 하는 다른 개발자에게도 같은 효과가 나는지가 2단계에서 확인할 핵심이다.

그래도 실제 공문 요청 건을 처리해 반영까지 했고, "예상 1주 → 실제 반나절"은 판단 기준(30% 단축)과 차이가 커서, 정식 실험과 확대 검토를 할 이유로는 충분하다.

## 1.3 실험 과제

조회형 화면 1본으로 한다. 조회형을 고른 이유는 다음과 같다.

- 정보화본부 화면 중 가장 흔한 유형이라 결과를 일반화하기 좋다.
- 트랜잭션·채번·결재 연동이 없어 변수가 적다.
- 그래도 검색조건, 그리드, 페이징, 코드 콤보, 엑셀 다운로드처럼 실무에 필요한 요소는 다 들어간다.

**과제 명세 (예시, 실제 과제로 바꿀 것)**

| 항목 | 내용 |
|------|------|
| 화면 | 학적 변동 이력 조회 |
| 검색조건 | 학년도, 학기, 소속(대학/학과 콤보 연동), 변동구분(공통코드), 학번/성명 |
| 결과 | 그리드 (학번, 성명, 소속, 변동구분, 변동일자, 사유), 서버 페이징, 엑셀 다운로드 |
| SP | 조회 SP 1개 (페이징 포함), 콤보용 공통코드 SP는 기존 것 재사용 |
| 권한 | 소속 학과 담당자는 자기 학과만 조회 |

명세서는 두 방식에 **똑같이** 준다. 명세가 다르면 비교가 의미 없다.

## 1.4 실험 설계

| 구분 | A: 기존 방식 | B: 에이전트 방식 |
|------|-------------|-----------------|
| 수행자 | 개발자 1명 | 다른 개발자 1명 (경력이 비슷한 사람) |
| 도구 | 기존 템플릿 복사, 수작업 | 7회차 에이전트 + 수작업 보정 |
| 산출물 | 화면 XML, SP, 단위 테스트 결과 | 같음 |
| 검수 | 같은 검수자, 같은 체크리스트 | 같음 |

**한계와 보완**

- 사람이 다르면 개인 역량 차이가 섞인다. 가능하면 과제를 2개 준비해 **교차(crossover)**로 진행한다. 개발자 X는 과제 1을 A로, 과제 2를 B로 하고 개발자 Y는 반대로 한다.
- 표본이 1~2건이라 통계적 결론은 아니다. "도입을 확대할지 결정하기 위한 첫 근거"로만 쓴다.

## 1.5 측정 지표

| 지표 | 정의 | 측정 방법 |
|------|------|----------|
| 총 소요 시간 | 명세 수령부터 검수 통과까지 걸린 순수 작업 시간 | 단계별로 시작·종료 시각 기록 |
| 단계별 시간 | 화면 / SP / 연동·디버깅 / 검수 지적 수정 | 위와 같음 |
| 검수 결함 수 | 검수자가 지적한 건수 (심각도 상·중·하) | 결함 기록표 |
| 게이트 위반 수 | ES5 검사, 개인정보 검사, SP 리뷰에서 걸린 건수 | 게이트 실행 로그 |
| 프롬프트 반복 횟수 | B만 해당. 에이전트에 다시 요청한 횟수 | 대화 로그 |
| 수작업 수정 비율 | B만 해당. 생성물 중 사람이 고친 줄 비율 | 생성 직후와 최종본의 diff |
| 체감 난이도 | 1~5점 | 수행자 설문 |
| 설명 스킬 사용 횟수 | B만 해당. 이해가 안 돼 설명을 요청한 횟수와 그 부분 | 대화 로그 |

"수작업 수정 비율"은 꼭 잰다. 시간이 줄었더라도 생성물의 절반을 고쳤다면, 에이전트가 만드는 것이 아니라 초안 템플릿 역할만 하고 있다는 뜻이기 때문이다.

## 1.7 판단 기준 (사전에 합의)

결과를 본 뒤 기준을 정하면 결론을 끼워 맞추게 되므로, **실험 전에** 다음을 합의해 둔다.

- 총 소요 시간이 **30% 이상** 줄고,
- 상·중 심각도 결함이 기존 방식보다 **많지 않으면**,
- 2단계(팀 시범 적용)로 넘어간다.

시간은 줄었는데 결함이 늘었다면, 게이트를 보강한 뒤 다시 실험한다.
