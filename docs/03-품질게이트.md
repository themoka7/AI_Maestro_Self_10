# 3. 품질 게이트

## 3.1 원칙

에이전트가 만든 코드는 **사람이 만든 코드보다 덜 믿는 것**에서 출발한다. 그럴듯해 보이는 코드가 빠르게 많이 나오기 때문에, 사람이 읽기 전에 기계가 먼저 거르는 단계를 둔다.

```
에이전트 생성 → [게이트 1: 자동 검사] → [게이트 2: SP 리뷰] → [게이트 3: 기존 검수] → 반영
                   ES5 문법                  체크리스트
                   개인정보 컬럼 접근          (사람)
                   SQL 정적 규칙
```

자동 검사는 **실패하면 다음 단계로 못 넘어가게** 건다. 경고만 띄우는 게이트는 몇 주 지나면 아무도 보지 않는다.

## 3.2 게이트 1-a: ES5 문법 검사

**왜 필요한가**: 에이전트는 최신 JS 코드를 많이 보고 학습했기 때문에 `const`, `let`, 화살표 함수, 템플릿 리터럴, `class`, 구조 분해 등을 자연스럽게 쓴다. 우리 WebSquare 화면은 ES5 기준이라 이런 문법이 섞이면 대상 브라우저나 엔진에서 깨진다.

**구현**: [`gates/es5/check-es5.js`](../gates/es5/check-es5.js)

- WebSquare XML 안의 `<script>` 블록(CDATA 포함)과 `.js` 파일을 뽑아 acorn으로 `ecmaVersion: 5` 파싱
- 파싱 오류가 나면 파일, 원본 기준 줄 번호, 해당 줄을 출력
- 문법은 ES5지만 런타임에 없는 API(`Promise`, `fetch`, `Array.prototype.includes`, `Object.assign` 등)는 별도 금지 목록으로 경고

**한계**: 정규식 기반 API 탐지라 주석이나 문자열 안의 단어도 잡을 수 있다. 오탐은 `// es5-ignore` 주석으로 그 줄만 제외한다.

## 3.3 게이트 1-b: 개인정보 컬럼 접근 검사

**왜 필요한가**: 조회 화면을 만들 때 에이전트는 "있으면 좋을 것 같은" 컬럼까지 SELECT에 넣는 경향이 있다. 주민번호·연락처·주소 같은 컬럼이 기획에 없이 조회 SP에 들어가면 개인정보 과다 조회가 된다.

**구현**: [`gates/pii/check_pii.py`](../gates/pii/check_pii.py)

- 민감 컬럼 목록([`pii_columns.txt`](../gates/pii/pii_columns.txt))을 기준으로 SQL 파일에서 해당 컬럼 참조를 찾는다
- 같은 파일에 승인 주석 `-- PII-APPROVED: <승인근거>`가 있고, 그 주석에 해당 컬럼이 적혀 있으면 통과
- 승인되지 않은 참조가 있으면 실패
- 컬럼 목록은 우리 DB 표준 용어사전(메타 시스템)에서 "개인정보" 분류된 컬럼을 추출해 만든다

**보완 과제**: SQL 정적 검사로는 `SELECT *`, 동적 SQL, 뷰를 거친 접근을 완벽히 막을 수 없다. 그래서 `SELECT *`는 무조건 실패 처리하고, 동적 SQL은 SP 리뷰 체크리스트에서 사람이 본다. 최종 방어선은 DB 권한(조회 계정의 컬럼 권한)과 접속 기록 관리 시스템이다.

## 3.4 게이트 1-c: SQL 정적 규칙 (추가 예정)

| 규칙 | 이유 |
|------|------|
| `SELECT *` 금지 | 컬럼 추가 시 의도치 않은 노출, 개인정보 검사 우회 |
| 동적 SQL에 파라미터 문자열 연결 금지 | SQL 인젝션 |
| 조회 SP에 권한 조건(소속 등) 필수 | 권한 밖 데이터 조회 |
| 페이징 없는 대용량 조회 금지 | 성능 |
| 명명 규칙 (SP 접두어, 파라미터 접두어) | 표준 준수 |

이 표의 규칙은 DBMS(Oracle/Tibero/MSSQL 등)에 맞춰 구현한다. 우선 `SELECT *` 금지는 PII 검사기에 포함해 두었다.

## 3.5 게이트 2: 생성 SP 리뷰 체크리스트

사람이 보는 단계다. 에이전트가 만든 SP는 아래 항목을 리뷰어가 확인하고 PR(또는 검수 요청서)에 체크 결과를 남긴다.

- [ ] 명세에 있는 컬럼만 조회하는가 (명세에 없는 컬럼이 있으면 이유 확인)
- [ ] 권한 조건이 WHERE에 있고, 파라미터로 우회되지 않는가
- [ ] 조인 조건이 빠져 카테시안 곱이 생길 여지가 없는가
- [ ] 유효 이력 조건(사용여부, 적용 시작·종료일 등)이 기존 SP와 같은 방식인가
- [ ] 공통코드 조회를 하드코딩하지 않고 공통 함수/뷰를 쓰는가
- [ ] 실행계획을 확인했고, 풀스캔이 있다면 근거가 있는가
- [ ] 예외 처리와 로깅이 표준 템플릿을 따르는가
- [ ] **에이전트가 지어낸 테이블·컬럼·함수가 없는가** (실제 스키마와 대조)

마지막 항목은 별도로 강조한다. LLM은 존재하지 않는 공통 함수나 컬럼을 그럴듯하게 만들어 낸다. 컴파일 단계에서 잡히는 경우가 대부분이지만, 동적 SQL 안에 있으면 실행해 봐야 드러난다.

## 3.6 어디에 거는가

| 단계 | 방법 | 비고 |
|------|------|------|
| 개인 PC | pre-commit 훅 | 1단계부터 |
| 공용 저장소 | CI (커밋/PR 시 실행) | 2단계부터 |
| 배포 전 | 기존 이행 검수 절차에 게이트 결과 첨부 | 3단계부터 |

에이전트 자체에도 같은 검사기를 도구로 쥐여 주면, 생성 직후 스스로 검사하고 고치게 할 수 있다. 사람에게 넘어오기 전에 걸러지는 양이 크게 늘어난다.

## 3.8 생성 → 검증 → 수정 루프

게이트를 사람이 돌리는 대신, 서브에이전트 [`gate-reviewer`](../.claude/agents/gate-reviewer.md)가 생성 직후에 돌린다.

- 두 게이트 실행 → 자동 수정 가능한 위반(ES5)만 고침 → 재검사, **최대 3회** 왕복
- **개인정보 위반은 고치지 않는다.** 승인 주석을 달지 않고, 컬럼을 지우지도 않는다. 수정안 두 가지를 적어 사람 확인으로 넘긴다.
- 남은 위반이 모두 사람 확인 대상이면 3회를 채우지 않고 멈춘다.
- 매 회차 게이트 출력 원문, 조치, 수정 전·후를 `logs/gate-review/`에 남긴다.
